# Memory Runtime

> Status: **read-only.** Implements the interfaces below; adds no write path — that part of "phase 1" never changed. What HAS changed since this document was first written: `MemoryRuntime` now optionally constructs and wires in the two accelerators `ACCELERATION_LAYER.md` describes (`tools/memory_index.py`'s lexical index, `tools/embedding_index.py` + a real backend's semantic index), each validated once at construction and passed through to every `retrieve()` call — see "The three modules" and "What this is not" below for the current shape. `ACCELERATION_LAYER.md` remains the authoritative design contract for acceleration semantics; this document never restates or overrides any of its invariants, and where the two could be read as disagreeing, `ACCELERATION_LAYER.md` wins.

## What this is

`MEMORY_PROTOCOL.md`'s `RETRIEVE` operation already describes two phases: a **search phase** that returns candidate notes, and a **validation phase** that checks each candidate's `memory_status`, supersession, and conflicts against live Markdown before anything is trusted. This is the concrete, dependency-free implementation of that shape, sitting between the canonical Vault and an AI/agent caller:

```
Canonical Vault (tools/validate-vault.py's Vault — discovery, frontmatter)
        v
tools/vault_identity.py     — path-aware, fail-closed note-identity resolution
tools/memory_retrieval.py   — search phase: query -> Candidates
        v
tools/memory_runtime.py     — validation phase + orchestration: Candidates -> ValidatedContext
```

**Retrieval never establishes truth.** A `Candidate` means "this note may be relevant" — it carries no `memory_status`, no trust judgment, nothing about currentness. Only `memory_runtime.py`'s validation step, which re-reads the live note and checks it against the vault's actual lifecycle state (superseded/candidate/uncertain/deprecated/disputed/cycle-member/absent), decides whether a result is `accepted`. A highly-ranked candidate cannot become "current" merely because retrieval ranked it highly — see `tests/test_memory_runtime.py`'s key-invariant test.

## The three modules

- **`tools/vault_identity.py`** — `resolve_identity(vault, raw)`: given a path-qualified or bare identity, returns the one note it names, or fails closed (`None`, `[]` for missing; `None`, `[candidates]` for ambiguous) — never a same-stem guess. Also `stem_matches()`, the deliberately looser "every note with this filename" lookup. Originally written inside `tools/audit_job_dependencies.py` for its P0-1 fix; extracted here so a second consumer doesn't carry a second copy of a security-relevant algorithm.
- **`tools/memory_retrieval.py`** — `search(vault, query, methods=None, limit=None, index=None, validated_index=None, embedding_backend=None, embedding_index=None, validated_embedding_index=None) -> list[Candidate]`. Five explicit, never-conflated methods: `exact` (fail-closed identity), `filename` (loose stem lookup, multiple results expected), `wikilink` (inbound-link graph, reusing `validate-vault.py`'s own `WIKILINK_RE`, optionally accelerated by `index`/`validated_index`), `text` (deterministic, word-boundary keyword scoring — never claimed or scored as semantic), and `semantic` (cosine similarity against a caller-supplied `embedding_backend`/`embedding_index` — a no-op, contributing nothing, unless both are explicitly provided; see `tools/embedding_backend.py` and `tools/embedding_index.py`). Deterministic ordering by an explicit sort key (method priority first, so a similarity score can never outrank a higher-priority method's hit), never filesystem/rglob order. Duplicate hits on the same note (matched by more than one method) merge into one `Candidate` recording every contributing method — `method_scores` keeps each method's own score separate — never a repeated entry.
- **`tools/memory_runtime.py`** — `MemoryRuntime(vault_root, boot=None, repo_root=None, index=None, embedding_backend=None, embedding_index=None)` exposes `resolve(identity)` (identity only), `inspect(identity)` (resolve + validate one note), `retrieve(query, ...)` (search + validate every candidate). If `index` and/or `embedding_backend`+`embedding_index` are supplied, each is validated exactly once at construction (a `ValidatedIndex`/`ValidatedEmbeddingIndex`, bound by object identity to this instance's own vault) and reused for every `retrieve()` call on this instance — see "What this is not" below for what that reuse does and doesn't change. Every returned `ValidatedContext` carries full provenance: canonical path, retrieval method(s), the source query, `memory_status`, a `status_track` explaining *why*, and `accepted: bool` — the one field that means "trustworthy right now." Rejected candidates (superseded, candidate, disputed, cycle-member, untracked) are still returned, correctly labeled, never silently dropped or promoted.

All three modules' own source: standard library only, no network access, no write method anywhere. `tests/test_memory_runtime.py` includes a static source check confirming none of these three files ever imports (or even mentions, in code or comment) an ML/vector-store package name — the two accelerators that DO carry such a dependency (`tools/embedding_index.py`'s optional real backend) live in separate files, constructed and injected by the caller, never imported here.

## What this is not

- Not itself an accelerator, and not required to have one. Every call still re-reads live Markdown for validation, regardless of whether an index or embedding index was supplied for the search phase. `index_snapshot_time` on every `Candidate` is always `None` here because this baseline retriever performs no caching of its own; a supplied accelerator narrows *which* notes get discovered, never *whether* a discovered note is trusted — validation runs against the live note every time either way (`ACCELERATION_LAYER.md` invariant #7).
- Not a write path. `WRITE_MEMORY`, `UPDATE_MEMORY`, `RESOLVE_CONFLICT`, and `CHECKPOINT` are untouched — this phase only ever reads. Deleting an accelerator's index (or never building one) leaves this runtime's behavior unchanged apart from search speed, per `ACCELERATION_LAYER.md` invariant #5.
- Not wired into `validate-vault.py`, `audit_health_coverage.py`, or `audit_job_dependencies.py`'s existing CLI behavior. Those tools work exactly as before; this is an additive capability, not a replacement.
- Not an autonomous agent. Three read-only questions — where is it, is it trustworthy, what matches — nothing else.
- Not a second authority. A candidate's similarity score, lexical match count, or method of discovery never influences `accepted` — that still comes exclusively from `inspect()`'s note-only validation, structurally blind to any score or index field (`tests/test_memory_index.py` and `tests/test_embedding_boundary.py`'s adversarial-authority cases exercise exactly this).

## Where semantic retrieval plugs in

`memory_retrieval.py`'s `search()` signature and `Candidate` shape were the seam this section originally described as future work — semantic retrieval is now implemented as the `semantic` method above (`_search_semantic()`, backed by `tools/embedding_backend.py` + `tools/embedding_index.py`, with `tools/sentence_transformers_backend.py` as the one real backend implementation this repository ships, an optional dependency — see `ACCELERATION_LAYER.md`). `memory_runtime.py`'s validation phase, `MemoryRuntime`'s public API, and every pre-existing caller (none of which pass the new parameters) are unaffected, because validation was never told to trust a method by name, only to re-check the note a method happened to point at. No `MEMORY_PROTOCOL.md` change was required for that addition. A future `graph` method would plug in the identical way.
